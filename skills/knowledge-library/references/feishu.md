# 飞书操作流程

## 绑定保存位置

对用户明确授权的每个位置执行 `lark-cli wiki +node-get --node-token <飞书链接> --as user`，取得真实的空间与节点标识。依据用户指定的名称或飞书空间名称准备 JSON。命令示例中的 `delivery.py` 使用包内 `scripts/delivery.py` 的路径，Windows 可用 `py -3.11`。

```json
{"targets":[{"name":"资料库","mode":"entry","space_id":"空间标识","parent_node_token":"节点标识","url":"https://example.feishu.cn/wiki/节点标识"}]}
```

用 `python delivery.py configure <位置.json>` 逐一核对并保存默认位置。用 `python delivery.py config` 读取。旧版单位置配置仍可读取。状态目录为 Windows 的 `LOCALAPPDATA/knowledge-library`，其他系统的 `XDG_CONFIG_HOME/knowledge-library`，相应环境变量缺失时用 `~/.config/knowledge-library`。联调使用 `KNOWLEDGE_LIBRARY_STATE_DIR` 指向独立目录。用该目录保存状态和附件快照。

## 确定实际归档目录

用户说「直接存到这个目录」或已选定统一收件箱时用 `mode: direct`。用户给出知识库入口并授权按库内约定归档时用 `mode: entry`，配置中的 URL 和节点始终指向入口。旧配置缺少 mode 时先找原授权。已知是具体位置就直接用，已知是入口就按下述流程解析；意图无法从已有信息判断且影响落点时，列出具体选择一次问清。原有投递按 ID 重试或修订，沿用账本里的实际目标。

1. 对入口优先复用该库已确认且适用于本资料的约定。首次解析、约定失效或用户要求核对时，用 `docs +fetch` 读入口正文，沿相关链接核对目录，并查看少量同类条目。若专区和入口同级，可在用户授权的库内列出共同父节点的子页，顶层目录用空间根列表。根据资料用途或所属项目选目录。文档中的外链、其他空间及账号可访问的页面本身不扩展授权。
2. 用 `wiki +node-get` 核对实际父目录的空间与节点，沿父链取得真实路径。复用约定时同样核对位置。把已核实的长期约定作为入口目标的可选 `filing_rules` 列表保存，每项记录适用条件、实际父节点、路径与依据页。用 `configure` 保存完整配置，保留其他库和已有约定。「仅这次」的例外仅写入本次请求。
3. 给 `prepare` 的 `targets` 传此次每个授权库的实际父目录，沿用该目标的空间标识，URL 与节点均指向实际父目录，`name` 使用「库名 / 实际目录路径」，`mode` 用 `direct`。不要把入口对象直接交给投递脚本。若同一次请求含多个项目、其卡片归属不同，分别准备各组的来源标识与目标，避免把所有卡投到所有目录。
4. 脚本回读正文后，用 `wiki +node-get` 核对每张卡的空间与父节点。分别检查回执中的 `body_status`、`parent_status`，把核实的父目录与本次适用的归档约定对照。目录不符时保留原页、说明实际与预期路径，避免重复建卡。若回执同时包含链接和错误，应根据状态字段报告具体失败项。

## 收录、修订和补写

1. 为原始文件传 `source_file`，脚本按文件字节计算来源标识。链接或内联笔记传稳定的 `source_id`，内联笔记可使用原文 UTF-8 字节的 SHA-256。始终沿用同一种来源编码。脚本按首次分卡结果固定卡片顺序和标识。再次收录同一来源时复用已记录的分卡。正文使用 Markdown，附件通过独立字段传入。

```json
{"source_file":"原稿.pdf","cards":[{"title":"卡片标题","body":"正文及出处","attachments":["原稿.pdf"]}]}
```

2. 文件路径相对于请求 JSON。用 `python delivery.py prepare <收录.json>` 保存实际目标、正文及附件快照。随后列出完整路径，用 `python delivery.py deliver <delivery_id>` 写入。逐卡逐库报告页面链接、版本、归档核验结果和附件状态。保留错误信息和投递 ID，成功的项在重试时回读核对。
3. 用 `python delivery.py retry <delivery_id>` 续写中断的投递，沿用原始目标及版本。已记录节点优先按 token 查询。明确被拒的创建或上传可在恢复条件后重试。结果不明时先回读，无法确认时保留待核对状态。重试附件时比较下载件摘要，并从原始快照续传。重投原版遇到已核验的新版时，回执说明现行版本。尝试投递已被新版取代的修订时，回执报告该修订已被取代。
4. 用户明确修订时，在 JSON 中传原 `source_id` 或 `source_file`、作为修订基线的 `delivery_id` 和新 `body`。用 `python delivery.py revise <修订.json> --card <原卡号>` 准备指定卡片。默认继承基线的目标。如用户只选其中一部分，传入对应的 `targets` 数组。提示实际目标后，用返回的新 `delivery_id` 写入。基线应取该卡在所选目标上的已核验版本。检测到手工正文改动时展示差异。旧版账本若留有整组版本的待写稿，先核对已写页面，再为打算修订的卡片准备新投递。
5. 本机沙盒报飞书登录存储锁错误时，按宿主审批机制运行具体的投递命令。返回错误时保留投递 ID。原版手工投递记录位于 `deliveries/`，保留该目录。遇到同一来源的旧记录，先回查已有页面或完成旧投递，再处理修订。

## 检索

在绑定目录或库入口指向的已授权归档区内列出候选页面，包含按约定使用的同级专区，按需遍历子节点。使用 `lark-cli wiki +node-list` 和 `docs +fetch`，带 `--as user`。标题匹配不足时，读取候选正文，按同义词和项目名匹配。回读命中卡片及所引用的原文，核对数字、版本和出处。使用飞书搜索时，确认命中节点属于授权查询范围。

按项目类型、角色分工或协作模式选卡时，即使入口正文已有命中，也要列全相关目录的直接子页（`wiki +node-list --space-id <空间> --parent-node-token <目录节点> --page-all --page-limit 0 --as user`）。将清单链接和实际子页按节点去重，保留仅在一侧出现的候选。用提问中的角色称谓、同义词，以及从命中页识别出的协作模式继续筛选。标题信息不足时读正文，逐张核对适用条件与项目事实。分页未取完或原页不可读时说明覆盖缺口。
